1. Problem statement and application context

Pingora is a community publishing platform: authors publish (or schedule) posts, readers like and comment on them in nested threads, follow authors, and become administrators through a request-and-approval process. The case study is a small social-publishing application (in the spirit of a blog or news community) chosen because it needs a rich set of relationships (1:N, M:N and two recursive ones) and several business rules that the database itself should guarantee. All persistent data lives in PostgreSQL; the application is a thin layer over it.

Intended users. Visitor — reads, searches and filters posts. Verified user — likes, comments, subscribes, requests admin rights. Administrator — writes and schedules posts, reviews admin requests, views the analytics and the Integrity Lab.

2. Main requirements and workflows

  • Functionality: register with e-mail and OTP or Google sign-in; create posts (rich-text JSON, image, tags, category), publish now or at a scheduled time (cron every minute); browse, search and filter with sorting and pagination; like; comment and reply to any depth; subscribe to authors (e-mail on new post); request, approve or reject admin rights; analytics for admins; delete own posts.
  • Business rules enforced by the DBMS: e-mail unique and well-formed; one like per user per post; one subscription per pair and never to oneself; non-blank title, comment and reason; views never negative; a scheduled post must have a publish time; a comment is never its own parent; OTP is a 6-digit number; request status is one of pending/approved/rejected; the platform always keeps at least one administrator.

Modelling notes. No weak entities: comments depend on a post (existence dependency, cascade) but have their own surrogate key. No specialization: admin vs. regular user differ by one flag and no extra attributes, so a boolean replaces an ISA hierarchy. Multivalued attribute tags is stored as an array (see section 6 for the normalized alternative). Derived attributes (likes, comments, subscribers counts) are computed by views, never stored.

Assumptions

  • Two kinds of account only, so the role is the boolean isadmin, not a roles table.
  • Deleting a user or post cascades to everything that depends on it.
  • Counts of likes, comments and subscribers are derived; posts.views is a stored counter because individual reads are not recorded.
  • A reply belongs to the same post as its parent; the application guarantees it (a composite foreign key would enforce it in the schema).
  • A scheduled post is hidden from every feed until scheduled_at passes.
  • Timestamps default to the DB clock; updated_at is maintained by triggers.

5. Normalization justification

FormArgument for Pingora
1NFEvery relation has a key and atomic attributes, with two deliberate exceptions: posts.tags TEXT[] (labels with no attributes of their own) and posts.content JSONB (one rich-text document, always read and written whole).
2NFEvery primary key is a single surrogate column, so no partial dependency exists.
3NFOnly user_id is stored in posts, likes and comments — never the author's name, e-mail or avatar — so there is no transitive dependency post → author → author attributes (storing them would cause update and deletion anomalies).
BCNFCandidate keys are {id} everywhere, plus {email} in users, {user_id, post_id} in likes and {user_id, author_id} in subscriptions; every determinant is a candidate key.

6. Design decisions, schema size and known trade-offs

  • Surrogate UUID keys keep identifiers unguessable in URLs; M:N relations are separate tables with a UNIQUE pair so duplicates are impossible. Self-referencing comments.parent_id models unlimited nesting; a recursive CTE reads the tree.
  • Why six tables. The domain has four entity sets and two M:N relationships, which map exactly to six relations; padding the schema with tables the application does not need would not improve the design. Our effort went into constraints, views, triggers, indexes and a transaction instead. We are aware of the scope guideline (8–12 tables) and document the five tables a fuller normalization would add.
  • Known weaknesses and the normalized alternative (written as commented-out SQL in schema.sql, section 5): tags array → tags + post_tags (1NF); free-text category → categories + FK; users.otp (no expiry, one at a time) → otp_codes; stored views counter → post_views; e-mail-only alerts → notifications. Adopting them raises the schema from 6 to 11–12 relations. We kept the simple structures so the running application is unchanged, and we can demonstrate the improved design.
  • Other trade-offs: a boolean role cannot record who approved whom (reviewed_by would); ON DELETE CASCADE is convenient but deletes content silently (soft delete is the alternative); the replies-to-same-post rule is not in the schema.

7. DBMS features implemented

FeatureObjects and purpose
Views (6)post_stats (likes, comments, engagement per post; counts in separate subqueries so joins do not multiply rows) · author_leaderboard (view on a view, RANK()) · trending_posts (ROW_NUMBER() OVER PARTITION) · comment_threads (recursive CTE) · admin_request_overview · user_activity_summary (correlated subqueries). All are read by the Reports page.
Triggers (6)set_updated_at() on users, posts, comments, admin_requests (BEFORE UPDATE). prevent_last_admin_loss() on users (BEFORE UPDATE OF isadmin, BEFORE DELETE): raises SQLSTATE 23001 if no other admin exists; it locks the other admin rows (FOR UPDATE) so two concurrent demotions cannot both succeed.
Indexes (15)B-tree and partial indexes for the feed (WHERE is_scheduled = FALSE), category pages, most-popular sort, the scheduler lookup, pending admin requests; foreign-key indexes (likes.post_id, comments.post_id/parent_id/user_id, subscriptions.author_id); GIN on tags; trigram GIN on title and description for ILIKE '%text%' search. On 50,000 posts, search drops from 29 ms to 0.5 ms and the category feed from 4.8 ms to 0.03 ms (EXPLAIN ANALYZE).
TransactionAdmin-request review (workflow 1): lock, three updates across two tables, COMMIT or ROLLBACK, on one pooled connection. The Integrity Lab also runs every scenario in BEGIN … ROLLBACK.
SQL queriesEight showcase queries in queries_demo.sql (join/GROUP BY/HAVING, scalar subquery, NOT EXISTS, RANK/LEAD, recursive CTE, FILTER aggregation, view aggregation, self-join); nine more drive the Reports page.

8. Architecture, technology stack and UI overview

Architecture: Browser ↔ React single-page app (:5173) ↔ Express REST API (:5000, JWT in an httpOnly cookie, parameterized SQL through a pg connection pool) ↔ PostgreSQL 17. Redis caches the public post listing; pgAdmin (:5050) is included for inspection. All five services run in one Docker Compose network; schema.sql, views.sql and seed.sql load automatically on first start. Stack: React (Vite, TypeScript), Zustand, TanStack Query, Tailwind CSS, shadcn/ui, Recharts; Node.js, Express; PostgreSQL 17 (uuid-ossp, pg_trgm, pgcrypto); Redis; Docker Compose.
